# Install Check

A Chrome extension for the moment before `npm install`. On an npmjs.com package page it reads the registry and
the build record, then tells you what each green signal on the page proves for that exact version, and what it
leaves out. Explanations run on Gemini Nano on your device through Firebase AI Logic; the cloud model is used only
when the device cannot run the model, or when you ask it to read the package's install-time code.

Built for #BuildHybridAI 2026 (Web / Chrome track).

## Why

npm shows a provenance badge, a Sigstore signature and a set of dist-tags. Developers read them as "safe to
install". Each one certifies something narrower, and none of them says what it leaves out. The numbers behind this
come from Emil Huseynov's own registry measurements (sources listed in the panel and in `src/evidence.js`):

- Provenance names the source commit (all 575 attestations studied do), but 76.7% were built from a branch, not a
  tag, and the build's action references can move after the fact: 62.6% of attested builds used at least one
  mutable action reference (37.9% excluding GitHub-owned actions, 19.6% excluding GitHub-owned and same-owner ones).
  Of the 194 attested releases published in the 18 days after GitHub's workflow lockfile went GA, 1 was built
  with one.
- A Sigstore entry usually does not point at inspectable source: 2.04% of Rekor entries name a public repository
  (7.57% excluding the dominant issuer), and 97.64% store only a digest of what was signed.
- `latest` is always moved by `npm publish`, but other tags are moved by hand: 89.7% of divergent tags in top
  packages point at a release older than `latest`, with a median staleness of 914 days for `next`, `beta` and
  `alpha`. `npm install pkg@next` can install older code than `npm install pkg`, and npm prints no warning.

Install Check computes the per-version facts live (attested commit and ref, the workflow file at that commit and
every `uses:` reference in it, `actions.lock` presence, certificate window, Rekor entry, tag ages, install hooks) and
puts each next to the measured context. No number in the UI is generated by a model.

## How it uses hybrid inference

| Task | Where it runs | Why |
| --- | --- | --- |
| Signal cards (what each signal certifies / does not) | No model | Deterministic, from the registry, GitHub and the attestation bundle |
| "In plain words" three-line summary | Gemini Nano on device (`PREFER_ON_DEVICE`) | Small input, private: which packages you look at stays on your machine |
| Questions about the package | Gemini Nano on device, streamed | Same; grounded only in the facts above |
| Summary or question with input over the Remote Config limit | Cloud Gemini (`ONLY_IN_CLOUD`) | Too large for the on-device context |
| Device has no model (or it is still downloading) | Cloud Gemini via the SDK's automatic fallback | Keeps the product working everywhere |
| Deep check: install scripts plus a file diff against the previous version | Cloud Gemini only, on request | Reads tens of thousands of characters of code; result is shared through Firestore |
| "On-device only" setting | Gemini Nano or nothing | User choice; cloud features are disabled with a reason shown |

Every AI answer shows which engine produced it (`inferenceSource` from Firebase AI Logic), the latency, and the
routing reason. The panel header shows live status of Nano and the cloud path.

## Firebase products

- **Firebase AI Logic** (Gemini Developer API backend): `getGenerativeModel` with `InferenceMode`
  `PREFER_ON_DEVICE`, `ONLY_ON_DEVICE` and `ONLY_IN_CLOUD`; structured JSON output on both paths
  (`responseConstraint` on device, `responseSchema` in the cloud); streaming answers; `initializeDeviceModel` for
  the one-time Nano download. Cloud model: `gemini-3.5-flash-lite`, set per task in Remote Config. On a 63,000-character
  deep-check input (esbuild 0.28.2) it answered in about 2 s, against 62 s for `gemini-4-hydrogen` and 99 s for
  `gemini-3.8-flash` (measured 16 Nov 2026), so the deep check uses it by default. If Remote Config names a slower
  deep model, a timeout retries on the light one.
- **App Check**: enforced for AI Logic and Firestore. A Chrome extension page cannot load reCAPTCHA (MV3 forbids
  remote code), so this build uses the App Check **debug provider** for development: the token is registered in
  the console and injected at build time from a git-ignored file. **Production choice**: a `CustomProvider` whose
  `getToken` calls a small token-minting endpoint (Cloud Function, `admin.appCheck().createToken(appId)`) that
  checks the request comes from the published extension ID and rate-limits per installation. The provider is
  already wired in `src/firebase.js`; set `APPCHECK_EXCHANGE_URL` at build time. Functions need the Blaze plan,
  which this Spark project does not have, so the endpoint is not deployed.
- **Cloud Firestore**: `verdicts/{package@version}` caches deep-check results, so the cloud reads a given tarball
  once for all users. Rules in `firestore.rules` validate the schema, forbid deletes and allow replacement only
  after 30 days.
- **Remote Config**: thresholds and model names without shipping a new build.

| Key | Default | Use |
| --- | --- | --- |
| `cloud_model_light` | `gemini-3.5-flash-lite` | Summary and questions when the cloud is used |
| `cloud_model_deep` | `gemini-3.5-flash-lite` | Deep check (switch to `gemini-3.8-flash` for a slower, deeper review) |
| `on_device_max_chars` | 9000 | Above this, route to the cloud |
| `on_device_timeout_s` | 30 | If Gemini Nano has not answered by then, the cloud answers (label says so) |
| `stale_tag_days` | 180 | A pre-release tag older than latest by this many days is flagged |
| `max_packument_mb` | 24 | Cap on the registry document read for publish dates |
| `deep_max_tarball_mb` | 15 | Largest tarball the deep check unpacks |
| `deep_max_chars` | 60000 | Code budget sent to the cloud |
| `deep_timeout_s` | 60 | When the deep model differs from the light one: after this, retry on the light model |
| `cache_ttl_days` | 30 | Age at which a cached verdict is ignored |

## Gemini Nano on real hardware

Tested on Chrome 157.0.8103.52 (Windows 11, RTX 5070 Laptop GPU) with the on-device model already installed
(`OptGuideOnDeviceModel`, base model v3Nano 2025.06.30.1229, 4,072 MB). On 16 Nov 2026 the unpacked build showed the
"In plain words" summary labelled "Gemini Nano · on device" on npmjs.com/package/react, so the hybrid path runs on
device there, with the cloud used only for the deep check.

The panel reads `LanguageModel.availability()` at start, loads the model in the background while the registry is
read, and shows the state under Settings and status. If it says `downloadable`, the panel offers a one-time
download. While a summary is being written, the label shows the engine and a running clock; if Gemini Nano has not
answered within `on_device_timeout_s`, the cloud answers and the label says why. The side panel's DevTools console
logs each step with the prefix `[Install Check]`.

## Try it without building

Download `install-check-judges.zip` from the
[latest release](https://github.com/emilhuseyn/install-check/releases/latest), unzip it, open `chrome://extensions`,
turn on Developer mode, choose **Load unpacked** and select the unzipped folder. Then open
https://www.npmjs.com/package/react and click **What do these signals prove?**, or open the panel from the toolbar
and type `react@beta`, `esbuild` or `core-js`. That build carries an App Check debug token for this project so the
cloud path works for judging; the token will be revoked after judging.

## Build and run

```bash
npm ci
```

```bash
npm run build
```

Then open `chrome://extensions`, turn on Developer mode, choose **Load unpacked** and select `dist/`. Visit any
package on npmjs.com (try `react`, `esbuild`, `fast-check`) or open the side panel from the toolbar and type a name
such as `react@beta`.

App Check for your own Firebase project: replace `firebase-config.json`, register a debug token under App Check >
Apps > Manage debug tokens, and put its value in `appcheck-debug-token.local` (or the `APPCHECK_DEBUG_TOKEN`
environment variable) before building. Deploy `firestore.rules`. Do not publish a build that contains a debug token.

```bash
npm test
```

## What leaves your device

- Always: the package name and version you look at go to `registry.npmjs.org` and `raw.githubusercontent.com`
  (public data), and the Firestore cache lookup for that version.
- Only when Nano is unavailable or the input is large: the facts summary goes to Gemini through Firebase AI Logic.
- Only when you press the deep-check button: the package's install scripts and a file diff go to Gemini.
- With "On-device only" on: nothing goes to a model outside your machine.

## Limits

- Workflow inputs are read from the entry workflow only; actions called inside composite actions or reusable
  workflows are not followed.
- `actions.lock` presence is checked at the attested commit; whether a repository enforces it is not visible.
- Very large registry documents (above `max_packument_mb`) are skipped, so tag ages are shown without dates.
- The model explains; it does not decide. Signal levels come from fixed rules in `src/findings.js`.

## Built during the submission period

Everything in this repository was written from 16 Nov 2026, inside the submission period, with AI coding
assistance (which the rules allow): the extension (content script, background worker, side panel), the fact

## Keys in this repository

`firebase-config.json` is the Firebase web app configuration. Its `apiKey` identifies the project to Google and is
not a secret (Firebase documents it as safe to ship in clients); access is controlled by App Check enforcement on
AI Logic and Firestore, and by `firestore.rules`. App Check debug tokens are never committed: the build reads them
from a git-ignored file.
